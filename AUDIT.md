# Аудит wtbot — итоговый отчёт

## 1. Вердикт

Проект работоспособен и местами написан аккуратно (параметризованный SQL, атомарная запись файлов с 0600, ограничение размеров ответов, дедупликация in-flight задач, изоляция рендера в worker-пуле), но у него отсутствует несколько базовых защитных слоёв. Самое опасное — не единичный баг, а три системных провала: (а) веб-панель и JSON-API слушают `0.0.0.0` вообще без аутентификации, отдавая пресенс-роутер живых людей и два state-changing POST; (б) автовычисление числа worker-потоков может превысить жёсткий лимит пула и убить процесс прямо на этапе ESM-импорта на любой машине с ≥10 логическими CPU и свободной памятью; (в) `npm test` красный в HEAD (3 из 44) и CI не существует, поэтому регрессионного сигнала нет вообще. Отдельно: запрос боя по hex-идентификатору делает полный скан таблицы `battles` объёмом 2.33 ГБ — замерено 61.8 с на холодном кэше в синхронном node:sqlite на главном потоке. Данные и секреты сегодня не утекли, RCE нет, потери данных нет — все находки это отказы доступности, деградация и гигиена.

## 2. Критичные и высокие проблемы

### H1. Полный скан `battles` на каждом просмотре боя (доступность, главный поток)
`src/db/index.ts:3038` (и то же самое в `:3111`, `:3147`)
Механизм: `WHERE session_id = ? OR session_hex = ?`. Индекс есть только на `session_id` (PK) и `idx_battles_start`. SQLite умеет OR-оптимизацию только когда индексируемы обе ветви — здесь `EXPLAIN QUERY PLAN` даёт ровно `SCAN battles`. Таблица содержит `events_blob BLOB` (замерено 2 233 613 160 байт на 15 907 строк), то есть скан читает весь b-tree. Путь: нажатие кнопки медиа в Discord → `src/wrpl/battle-media.ts:233/326` → `reconstructBattle` → `getBattleForRender`; и `src/bot/commands/battle.ts:115` → `getBattleSummaryForRender`. node:sqlite синхронный, значит блокируется event loop вместе с Discord-heartbeat и Fastify. Замер: 61.8 с холодно / 70 мс тепло.
Исправление: `CREATE INDEX IF NOT EXISTS idx_battles_session_hex ON battles (session_hex);` в блок схемы. Ещё лучше — резолвить hex→decimal один раз на входе и запрашивать только по PK.

### H2. Автоплан worker-потоков не ограничен лимитом пула → падение при импорте модуля
`src/runtime-options.ts:122-125` + `src/workers/pool.ts:141`, `:595`
Механизм: `workerResourcePlan()` ограничивает `workerThreads` только числом CPU (`availableCpus - reservedCpus`) и памятью; `MAX_CONFIGURABLE_WORKERS = 8` (`pool.ts:98`) не применяется нигде — grep находит константу только внутри pool.ts. Конструктор `CpuWorkerPool` бросает на `size > 8`, а `const pool = new CpuWorkerPool()` выполняется на верхнем уровне модуля, который `src/index.ts:9` импортирует — то есть throw происходит во время ESM-эвалуации, до `initDb`, вне любого try/catch, без обработчиков `uncaughtException`. Worker-треды тоже умирают: `entry.ts` → `render-battle.js` → `pool.js`. На этой машине: `availableParallelism()=12`, `totalmem=16334 МБ` → `cpuLimited=11`; при свободных ≥8.2 ГБ `memoryLimited≥9` → `automaticThreads≥9 > 8` → `Число CPU workers должно быть целым от 1 до 8`. Явный режим не спасает: `integerSetting` ограничивает `WT_WORKER_THREADS` только числом CPU, поэтому `9..12` тоже бросает. Собственный смоук-тест проекта (`src/analysis/worker-smoke.ts:62-63`) **утверждает** значение 11 для 12 CPU/16 ГБ — то есть документированный автоплан заведомо вне допустимого диапазона пула. Локально маскируется тем, что в `.env` прибито `WT_WORKER_THREADS=8`; в `.env.example:81` стоит закомментированный `auto`, то есть свежий клон не стартует. Отказ недетерминированный: при нехватке свободной RAM (`memoryLimited=1`) тот же хост запускается нормально.
Исправление: экспортировать лимит и применить `Math.min(automaticThreads, MAX_WORKER_THREADS)` в `runtime-options.ts` (и к `max` явной ветки); заменить throw в конструкторе на клемп; сделать синглтон ленивым (`getPool()`), чтобы конфиг-ошибка приходила как отказ задачи, а не как крах импорта во всех тредах; поправить ассерт в worker-smoke.

### H3. Веб-панель и API на всех интерфейсах без какой-либо аутентификации
`src/index.ts:62` (в другом срезе файла — `:88`; файл менялся во время аудита), `src/web/index.ts:7-15`
Три независимых прохода нашли одно и то же — объединено. Механизм: `host: '0.0.0.0'` жёстко зашит, `PORT` по умолчанию 3000 (`src/config.ts:52`). Grep по `src/web` на `onRequest|preHandler|addHook|helmet|cors|csrf|authorization` не даёт ни одного хука. Открытые маршруты: `/`, `GET /api/stats`, `GET /api/items`, `GET /api/parsers/:source/history`, `GET /api/voice`, `POST /api/voice/refresh`, `POST /api/player-stats`. `GET /api/voice` (`src/web/routes/api.ts:58-96`) отдаёт живой ростер присутствия — `guildName`, `channelName`, `displayName`, `wtNick`, `joinedAt`, клан-тег, рейтинг. `GET /api/items` отдаёт сырой `data` записей wt-replays, включая маппинг анонимизированный ник → реальный ник из `realNamesFromItem` (`src/wrpl/replay.ts:238`). Reverse-proxy/Dockerfile в репозитории нет — деплой это `npm start`.
Противоречие в исходных находках, которое надо зафиксировать: сценарий «зациклить curl и сжечь WT-сессию оператора» **опровергнут**. `POST /api/voice/refresh` дедуплицируется `voiceRefreshInFlight` + 5 с троттл (`api.ts:100-119`), а дорогая часть отдельно ограничена `FORCE_THROTTLE_MS = 15_000` и `refreshInFlight` в `src/bot/voice-tracker.ts:178-190`. `POST /api/player-stats` имеет per-IP 20/мин и глобальный 60/мин (`src/web/routes/player-stats.ts:5-7,75-96`) и резолвит только уже известных локально игроков — это не открытый скрейпинг-прокси. Реальный ущерб — неаутентифицированное чтение персональных данных сообщества и бесплатный лёгкий DoS-ресурс.
Также известно, что это осознанно принятое ограничение: `AGENTS.md:433-434` прямо пишет «Web сейчас слушает `0.0.0.0` и не имеет auth. Не выставляй порт наружу без reverse proxy/auth». Это снижает «неожиданность», но не риск деплоя.
Исправление: `host: process.env['WEB_HOST'] ?? '127.0.0.1'`, а `0.0.0.0` — только явным opt-in; при не-loopback хосте требовать `onRequest`-хук с общим секретом (`WEB_TOKEN`, сравнение через `crypto.timingSafeEqual`) минимум на оба POST.

**H3a (тот же периметр). CSRF на `POST /api/voice/refresh`** — `src/web/routes/api.ts:100`. Маршрут не объявляет схему тела, не проверяет `Origin`/`Referer`/`Sec-Fetch-Site` и не требует Content-Type. Безтелесный кросс-доменный `fetch(..., {method:'POST', mode:'no-cors'})` или автосабмит-форма — это CORS simple request: браузер отправляет её без preflight, отсутствие CORS-заголовков мешает только чтению ответа, не side-effect'у. `POST /api/player-stats` защищён случайно — его JSON-схема заставляет ставить `content-type: application/json`, что вызывает preflight. Эксплуатируется и после привязки к 127.0.0.1, потому что запрос идёт из браузера оператора. Ущерб ограничен теми же троттлами (≤1 Discord-снапшот / 5 с, ≤1 WT-фетч / 15 с).
Исправление: тот же `onRequest`-хук — отклонять запросы с чужим `Origin` либо требовать заголовок `x-wtbot-csrf`.

**H3b (тот же периметр). Сырые тексты исключений уходят клиенту и не логируются нигде** — `src/web/index.ts:8` (`fastify({ logger: false })`), `src/web/routes/api.ts:50`, `src/parsers/index.ts:31-34`. `setErrorHandler` отсутствует во всём репозитории, поэтому работает `defaultErrorHandler` (node_modules/fastify/lib/error-handler.js:76-81): он вызывает `reply.log.error(...)` (это no-op из-за `abstract-logging`, logger-factory.js:85-91) и затем `reply.send(error)` с `message: error.message`. Обработчики в `api.ts` не имеют try/catch и дёргают синхронные читатели node:sqlite. Итог: единственная копия ошибки уходит анонимному клиенту, на сервере — тишина. Плюс `recordParseResult` сохраняет `err.message` без фильтрации, а `withFileLock` (`wt-cookies.ts:118,122`) перебрасывает сырой `ErrnoException` с абсолютным путём — он затем отдаётся на `/api/stats` и `/api/parsers/wt-replays/history`. (Уточнение: `wt-cookies` **не** является parser source — `/api/parsers/wt-cookies/history` всегда пуст; ошибка всплывает под именем `wt-replays`.)
Исправление: `app.setErrorHandler(...)` в `buildServer` — логировать всё в console.error, отдавать `message` только для 4xx, для 5xx — обобщённый текст.

### H4. `npm test` красный в HEAD, CI нет, один spec-файл вообще не запускается
`src/wrpl/render-heatmap.test.ts:538`, `:677`, `src/wrpl/render-battle-log.test.ts:76`; `package.json:17`; `tsconfig.json:49`
Механизм: воспроизведено — `tests 44 / pass 41 / fail 3`, стабильно. `git status --short` не содержит ни `render-heatmap.ts`, ни `render-battle-log.ts`, ни падающих тестов, то есть красное состояние закоммичено в HEAD (7d65ee4). Строка `#f04a50` встречается только в тесте и ни в одном исходнике; `PATH_COLORS` (`render-heatmap.ts:46-67`) — новая палитра, старая закомментирована на `:69-90`. `render-battle-log.ts` эмитит `<tspan>` только на `:238-239` и никогда не пишет `font-family="symbols_skyquake"`. Каталога `.github` нет. Дополнительно: `src/wrpl/render-heatmap.spec.ts` не запускается никогда (`package.json:17` глобит только `*.test.ts`) и не тайпчекается (`tsconfig.json:49` исключает `**/*.spec.ts`) — это единственное покрытие `mergeNearbyCamps`, `routeStrokeParts`, `segmentIntersection`; вручную даёт 3 pass.
Последствие: разработчик видит `fail 3`, узнаёт знакомые имена и коммитит — новая регрессия в рендере неотличима от фонового шума. Плюс сегодня неизвестно, действительно ли клановые маршруты рисуются правильным цветом.
Исправление: (1) починить/обновить три ассерта, перейдя на `data-*`-атрибуты и относительные проверки (сравнить `stroke=` игрока в overview и в clan-виде, вместо литерального hex); (2) `tsx --test "src/**/*.{test,spec}.ts"` и убрать `**/*.spec.ts` из tsconfig exclude; (3) добавить `.github/workflows/ci.yml` с `npm run build && npm test && npm audit --omit=dev`.

### H5. Плановый прогон wt-replays без ограничения страниц — многочасовой обход всего архива на холодной БД
`src/parsers/sources/wt-replays.ts:172`, вызов на `:224-229`
Механизм: `for (let page = 1; opts.maxPages === undefined || page <= opts.maxPages; page++)` — плановый вызов передаёт только `stopAtKnown: true` / `fetchDetails: false`. Три выхода из цикла: cutoff по `sinceTs` (мёртв — `sinceTs` не передаётся), `data.items.length < 20` (конец всего архива сайта) и `stopAtKnown && unseenOnPage < data.items.length` (нужна хотя бы одна уже известная сессия на странице). На пустой таблице `wt-replays` каждая запись неизвестна, значит третий выход не срабатывает никогда. Массив `fresh` накапливает все объекты `WtReplay` с вложенными `players` до самого конца обхода. Для сравнения `src/parsers/backfill.ts:25` всегда считает `Math.min(500, ...)`. Осиротевший doc-комментарий `wt-replays.ts:24-29` описывает удалённую константу лимита страниц.
Последствие: первый запуск / любой сброс БД / смена формата sessionId → тысячи последовательных POST с интервалом `REQUEST_INTERVAL_MS = 1500` мс (оценка ~8600 страниц ≈ 3.6 часа), рост RSS, забитая глобальная очередь запросов (голодание wt-players), и при этом `running`-сет блокирует повторный вход, а результат парсера не записывается вообще.
Исправление: передать явный `maxPages` (например 50) в плановом пути, вернуть `sinceTs`-окно, восстановить константу лимита и логировать `hitCap` как предупреждение в summary.

## 3. Средние проблемы

- **Дублирование identity при появлении `wt_user_id`.** `src/player-stats/comparison.ts:259`. `stableGroups` строится только из матчей с непустым `wtUserId`, поэтому уже созданная nick-only identity (`wt_user_id IS NULL`) в него не попадает, её `match.identityId` игнорируется, и `savePlayerIdentity` (`src/db/index.ts:1689-1721`) делает `INSERT` второй строки. Вся история `player_external_snapshots`/`totals` становится недостижимой, провайдер собирает заново, merge-процедуры в проекте нет. Ветка fallback (`:280-296`) при этом `identityId` использует — внутреннее противоречие. Фикс: если ровно одна nick-only identity среди матчей — передавать её `identityId` (промоушен строки), при нескольких — вернуть `ambiguous`.
- **`categoryOf()` кладёт нераспознанные строки в бакет `'all'` и затирает branch-итог.** `src/player-stats/normalizer.ts:226-228`. Проверено исполнением: `/(?:\bship\b|корабл)/i` не матчит `Naval battles in ships` (после `p` стоит `s`, `\b` не срабатывает), поэтому строка попадает в тот же бакет, что и `Naval battles`, а присваивание безусловное — побеждает последняя. Итог: `all.respawns = 71` вместо 520, `ships.respawns = null` при 10 ч наигранного времени; эти числа пишутся в `player_external_totals` и, из-за дедупликации снапшотов, не исправляются никогда. Тот же клоббер сработает на любой новой строке Gaijin в секции. Фикс: `/(?:\bships?\b|корабл)/i`; `categoryOf` должна возвращать `null` для нераспознанного, а присваивание — не перетирать уже установленное не-null значение.
- **`deserializeIdFields32` — настоящий бесконечный цикл на маске ≥2³²**. `src/wrpl/packet-stream.ts:140`. Воспроизведено: `readCompressed()` возвращает JS-double без ограничения, а `>>>`/`&` приводят к uint32; для `fields = 2**32` внешнее `while (fields > 0)` истинно, а бит не находится никогда, `fieldNum++` крутится вечно (проверено: >50 млн итераций; отдельный прогон реальной функции убит по таймауту 8 с, exit 124). Достижимо из `replay-events.ts:671/673` (сигнатуры `02 58 58 f0` / `02 58 56 f0`). Не бросает, поэтому try/catch на `replay-events.ts:687` не помогает. Сдерживается только тем, что парсинг живёт в CPU-воркере, а `pool.ts:472-503` делает `terminate()` по таймауту 45/90/180 с. Фикс: `fields = fields >>> 0` + проверка `Number.isSafeInteger`/диапазона + `fieldNum < 32`.
- **`BitReader.readBits`: bounds-check считается через 32-битный `>>`.** `src/wrpl/bit-reader.ts:35`. Проверено на реальном классе: `readBytes(2**29)` вернул буфер нулевой длины, оставил `bitOffset = 4294967296`, следующий `readU16()` вернул `0xabab` — то есть читатель молча перематывается на нулевой байт вместо EOF. Достижимо из `ecs.ts:199-200`, `gm-sync.ts:137`, `replay-events.ts:150`. Фикс: валидировать `bits` до арифметики и считать конец через `Math.ceil((bitOffset + bits) / 8)`.
- **`readCompressed` может вернуть Infinity/NaN, `ignoreBits` его фиксирует.** `src/wrpl/bit-reader.ts:90`, `:24-26`. Нет потолка на shift: ~147 байт с битом продолжения → `2 ** shift = Infinity`. Дальше `(Infinity + n + 7) >> 3 === 0`, guard проходит, `Infinity & 7 === 0` — быстрый путь, и читатель навсегда становится генератором `data[0]`. Проверено: три `readByte()` подряд вернули 255 при `bitOffset = Infinity`; из этого состояния `readCstr()` крутит бесконечный push в массив до смерти кучи воркера. Достижимо через любой `*StorageComponent` (`ecs.ts:346-354`) и через прямые присваивания `r.bitOffset = ...` в `packet-stream.ts:132/135/144/168/176/183/188`. Фикс: `if (shift > 56) throw`, а `ignoreBits`/`ignoreBytes` сделать валидирующими.
- **`lz4DecompressBlock` молча возвращает усечённый результат.** `src/wrpl/lz4.ts:20`, `:26`, `:37`. `src[s++]!` — только компайл-тайм; на выходе за буфер получается `undefined`, `litLen`/`matchLen` становятся `NaN`, а все guard'ы сравнивают с NaN и потому всегда false. Проверено: `lz4DecompressBlock(Buffer.from([0x1f,0x41,0x01,0x00,0xff]), 1024)` → `<Buffer 41>` без ошибки; `Buffer.from([0xf0,0xff,0xff])` → `RangeError [ERR_OUT_OF_RANGE]` из node:buffer вместо доменной ошибки. Отдельно `:26` читает `src[s+1]` за концом (break на `:24` гарантирует только один байт), `undefined << 8 === 0`, offset фабрикуется из одного байта и проходит валидацию. Фикс: явные bounds-check в обоих do/while, `Number.isInteger` перед guard'ами, `if (s + 2 > src.length) break`.
- **Таймаут исполнения в пуле не помечен как retryable.** `src/workers/pool.ts:485`. Один таймер покрывает и очередь, и исполнение (комментарий `:217-218`), но очередная ветка отдаёт `WorkerPoolError('QUEUE_TIMEOUT')`, а исполняющая — голый `new Error(...)`. `isWorkerPoolSchedulingError()` (`:608-617`) её не распознаёт, поэтому `src/wrpl/ingest.ts:145-156` идёт в `markBattleIngest(..., 'error')`, а `src/bot/battle-announcer.ts:112-123` — в `markAnnounce(..., 'failed')`, сжигая попытку. Три перегрузки подряд — реплей помечен окончательно битым. Фикс: код `EXEC_TIMEOUT` и включение его в `isWorkerPoolSchedulingError`.
- **5 непропатченных уязвимостей в prod-зависимостях (3 high), все с доступным фиксом.** `package.json:47`. `npm audit --omit=dev` воспроизводит: fast-uri, find-my-way, undici (high) + discord.js/@discordjs/rest (moderate); caret-диапазоны уже допускают исправленные версии — устарел только lock. Заявленный эксплойт-путь **опровергнут**: GHSA-c96f-x56v-gq3h — это HTTP/2 DDoS, а сервер работает на HTTP/1.1 (`http2` в `src/web` не встречается); undici-проблемы лежат на исходящих вызовах к API Discord. Это долг обслуживания, а не эксплуатируемая дыра. Фикс: `npm audit fix` + `discord.js` до `^14.27.0`, коммит lock-файла.
- **`data.rar` (1.2 ГБ) не попадает под .gitignore.** `.gitignore:5`. ## 5. Системные слабости

1. **Нет валидации границ на входе всех бинарных парсеров.** `bit-reader.ts`, `packet-stream.ts`, `lz4.ts`, `ecs.ts` систематически используют `src[s++]!` и non-null assertions как замену рантайм-проверкам, а также 32-битные операторы (`>>`, `>>>`, `&`) над значениями, которые физически являются JS-double и могут быть ≥2³², Infinity или NaN. Итог одинаков во всех четырёх файлах: guard проходит, arithmetic заворачивается, и вместо исключения получается либо бесконечный цикл, либо молча искажённые данные. Это одна ошибка, повторённая пять раз, — и `blk.ts`/`gm-sync.ts` показывают, что автор умеет писать защитно, просто делал это не везде.
2. **Нет верхней границы на всё, что растёт.** Отсутствуют: `maxPages` в плановом обходе wt-replays, `maxOutputLength` во всех zlib/zstd, ретенция `clan_rating_snapshots` и `player_external_snapshots`, LIMIT в `getClanRatingsWithDelta` и `seedWtPlayerSnapshots`, лимит строк в панели хитмапа, cap на длину summary перед embed-полем, уборка `*.tmp`. Каждый случай по отдельности мал; общий паттерн — ресурс ограничивается только тем, что данных пока мало.
3. **Отсутствие recovery-логики у механизмов, спроектированных с расчётом на сбой.** Файловый лок пишет `pid` и `createdAt` и не читает их. Пул страниц браузера имеет очередь ожидания без дедлайна и без reject. `ensureBrowser` ловит ошибку и не закрывает то, что уже создал. Миграции ловят ошибку и не смотрят, какая она. Везде диагностические данные собираются и выбрасываются.
4. **Наблюдаемость выключена там, где ошибки чаще всего случаются.** `fastify({ logger: false })` без `setErrorHandler` (500-ки уходят клиенту и не логируются), `InteractionCreate` глотает reject без параметра, нет слушателей shard-событий Discord, нет `unhandledRejection`. Оператор физически не может отличить сбой Discord от зависшего event loop или от переполненного диска.
5. **Периметр без аутентификации как архитектурное решение по умолчанию.** Не только `0.0.0.0` без хуков, но и отсутствие CSRF-защиты, CORS-политики, проверки `Origin`, и тот факт, что единственная защита `POST /api/player-stats` — побочный эффект JSON-схемы. Троттлы во внутренних сервисах компенсируют это случайно, а не по замыслу.
6. **Тесты не покрывают ни один слой, где реально живут дефекты.** 44 теста на 27 092 строк; ноль тестов на `src/db` (3266), `src/web` (787), планировщик пула, `bit-reader`/`lz4`/`blk`/`packet-stream`/`ecs`/`replay-events`. Существующие тесты рендера — подстрочные `includes` на нулевых фикстурах. 216 рабочих ассертов лежат вне `npm test`. Один spec-файл выпал одновременно из tsconfig и из тест-глоба. Сама сюита красная в HEAD, CI нет. Это причина, по которой находки 1–3 дожили до аудита.
