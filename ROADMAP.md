## Эксплуатация

1. **Копии БД на другом носителе.** Бот с 2026-09-29 работает в Docker на
   домашнем Linux-сервере, но `./backups` лежит на том же диске, что и база.
   База растёт на ~230 МБ в сутки (почти всё — `events_blob`), три копии
   занимают ~18 ГБ.
2. **`data/data/`** (~480 МБ, переехал с Windows вместе с `data/`) — старая
   копия каталога данных, в том числе прежний `wt-cookies.json`. В `replays/`
   части 28 боёв: 8 уже разобраны, 19 нет (14 `expired`, 5 `error`; с CDN их
   уже не скачать). Решить, разбирать ли их вручную, и затем удалить каталог.
3. **Сезон с форума**: источник `wt-clan-season` при смене формата поста
   начнёт падать с ошибкой разбора (видно на дашборде) — тогда поправить
   `src/clan-season-forum.ts`, прежнее расписание в БД при этом сохраняется.
4. **Публичный доступ к сайту**: туннель от сервера до внешнего reverse proxy
   поднят, `WEB_TRUST_PROXY` задан; на прокси осталось настроить сайт и TLS
   (инструкцию с адресами не коммитить: репозиторий публичный). Восстановление
   после перезагрузки сервера и смены его IP не проверялось.
   `GET /api/player-stats` при промахе кэша ставит lazy-запрос
   к внешнему источнику через браузерный транспорт — для анонимных посетителей
   это надо отключить (`WT_PLAYER_STATS_ENABLED=false`) или держать сайт за
   токеном. Discord OAuth — отдельное решение.
5. **Свежесть образа.** Chromium и пакеты Debian обновляются только пересборкой
   без кэша (README, «Боевой запуск в Docker»); решить, делать её вручную или
   таймером systemd, и в какое время (перезапуск ненадолго останавливает анонсы).

## Код

- `buildClanSnapshot` всё ещё синхронный на main thread: на HDD первый холодный
  запрос после старта занимал 7–15 с и блокировал Discord. На боевом NVMe
  (2026-10-01) холодные `/api/clans` и `/api/site-stats` — ~0,2 с, но это всё
  ещё ~200 мс main thread раз в минуту при активном сайте: нужна latest-state
  таблица рейтингов или worker-задача.
- ECS 2.59: нет сериализатора для нового типа `0xcfad499d` (подвесное
  вооружение `rocket`/`payload`) и часть `ri_gpu_object` не разбирается.
  На убийства и траектории не влияет (сущности изолированы), но эти
  сущности пропадают.
- Миграции: сезонные таблицы и часть индексов создаются bootstrap DDL вне
  реестра `PRAGMA user_version`; в боевой БД есть `clan_poll_log` и снимки
  `thunderinsights`, о которых код не знает.
- `events_blob` в таблице `battles`: полный проход по ней на холодном HDD — 50 с.
  Вынос в `battle_events` — отдельная офлайн-миграция после замеров.
- Избыточные индексы (`idx_bp_clan` ⊂ `idx_bp_clan_session`), `ANALYZE` не
  запускался — менять только с проверкой планов на копии боевой БД.
- Ретенция `clan_rating_snapshots`, `clan_rating_history` и `player_external_snapshots`.
- 11 боёв (6 — версии 2.59) без победителя при полном реплее: другого
  источника победителя нет, причину не выясняли. Обрезанные бои и фантомные
  боты удалены миграцией v9, слоты `coop/Bot…` исключены из статистики игрока.
- StatShark хранит режим как `simulator`, остальной код — `simulation`; фраги
  официального профиля и StatShark считаются по-разному (расхождение до 12×),
  сравнимы только бои, победы и поражения.
- Web: `@fastify/compress` для крупных JSON (`/api/vehicles` ~226 КБ в 43 КБ
  gzip), ETag для неизменяемых ответов.
- Дашборд `/`: ~700 строк inline-скрипта в `src/web/routes/pages.ts` без
  типизации — вынести в отдельный `.ts`, собираемый `tsc`.
- SPA: `GET /app/` (со слэшем) отдаёт 403 — `@fastify/static` с
  `index: false` не отдаёт index.html для корня префикса; нужен явный маршрут
  как у `/app`. Название сезона с форума собирается по-русски
  (`src/clan-season-forum.ts`, «Сезон дд.мм.гггг — …») и так же видно в
  EN/DE/FR/ES — подпись лучше строить на клиенте из дат сезона.
- SPA, доступность: маркеры таймлайна и строки ленты событий в
  `ScenePlayer.tsx` — `<span>`/`<div>` с `onClick`, без клавиатуры; заменить на
  `<button type="button">`. Стрелки в `SegControl`.
- Крупные функции: `buildHeatmapSvg` (712 строк), `extractReplayEventsProfiled`,
  `src/db/index.ts` (~5000 строк) — разбивать после стабилизации.

## Тесты

- `announce_state`: exactly-once, attempts, монотонность baseline.
- Реестр миграций (`PRAGMA user_version`) по версиям.
- Планировщик worker pool с фейковой фабрикой worker-ов и фейковыми часами.
- Full WRPL/ECS/GMSync fuzz и граничные случаи распаковки.
- Многоигроковые render fixtures: ненулевые значения, сортировка, 32 игрока.
- `src/player-stats/service.ts` покрыт только smoke-скриптами.
- Frontend: тестов и test setup нет (error-состояния, сброс
  `vehicleDictPromise` после отказа, пагинация боёв).

## Сбор и показ статистики (начато 2026-09-29)

- **БР техники из датамайна.** `economicRankArcade/Historical/Simulation` из
  `wpcost.blkx` → `VehicleInfo.br` (БР = ранг / 3 + 1). Словарь
  `wt-vehicles.json` сейчас собирается один раз навсегда — нужны версия
  формата и срок годности (БР меняется с патчами). Затем БР на сайте и
  проверка недельных лимитов этапов сезона по технике в боях (в воркере сводки).
- **StatShark на странице игрока.** `raw_json` снимка уже хранит всё:
  `leaderboardHistory` (место в глобальном рейтинге по режимам, ~20 точек за
  полтора года), `Misc.NameHistory`/`SquadronHistory`, дату регистрации,
  последний вход, рейтинги `ratingsNeo`. Извлекать при сохранении снимка
  (разбор крупного JSON не на main thread) и показывать. `vehicleHistory`
  хранит поля числовыми кодами без расшифровки — не показывать наугад.
- **`_id` клана как ключ.** Номер клана с лидерборда не меняется вместе с
  тегом; связать по нему кланы, сменившие ядро тега, вместо `clan_core`
  (ростер, история рейтинга, бои под старым тегом). Номер собирается с
  2026-10-01; пока ни один номер не встречался под двумя тегами.
- **Ещё не собирается** (решить, нужно ли): поиск игроков `searchplayers`
  (до 100 ников по началу, только ник; нужен браузер) — подсказка ника для
  `/api/player-stats`; рейтинг игроков `community/leaderboard` (топ-2020 по
  режиму и сортировке, числа округлены до «105.0K»); WTCS
  `text/wtcsleaderboard` (киберспорт); `clan_activity_by_periods` (смысл
  неясен).

## Продукт

Данные для всего ниже уже собраны; считать агрегаты на ingest или фоном, не
по HTTP-запросу.

- **Метастатистика техники**: win rate и K/D по машине, матрица «кто кого
  убивает» (`battle_kills.killer_model × victim_model`), эффективность оружия
  (`weapon`), техника по карте. Источник классов — `data/wt-vehicles.json`.
- **Ветка боя** (`air`/`ground`/`mixed`) из `battle_players.vehicles` и словаря
  техники, поле `battles.branch` и серверный фильтр. По данным на 2026-09-28
  все бои — наземные с авиацией, поэтому ценность низкая до появления других
  режимов.
- **Клан против клана**: история встреч, серии, средний счёт по противнику
  (`battle_players.clan_tag`, `team`, `battles.team_won`).
- **Карты**: словарь `levels/*.bin` → человеческое название, затем win rate
  стороны, длительность и места смертей (`battle_kills.victim_x/y/z`).
- **Внешняя статистика игроков**: решить, развивать или заморозить (3 identity,
  витрины не строить до реальных данных).
- **Чат боёв**: не публиковать без решения о приватности и явного API-контракта.
- **Нельзя**: аналитика отрядов — `battle_players.squad_id` по факту маркер
  команды (4096/4097), а не отряда. Postgres, Rust и GPU — не цели сами по себе.

Сырые наблюдения о качестве данных реплеев —
[docs/replay-data-quality.md](docs/replay-data-quality.md).
