## Эксплуатация

1. **Копии БД на другом носителе.** Бот с 2026-09-29 работает в Docker на
   домашнем Linux-сервере, `./backups` — на том же диске, что и база. База
   после перевода блобов событий в колоночный формат (2026-10-02) — ~1,3 ГиБ,
   растёт на ~1 800 боёв и ~57 МиБ в сутки (~20 ГиБ в год). Три копии сейчас
   ~18 ГБ (сняты до перевода), после ротации к 2026-10-05 — ~4 ГБ
   (`docs/database.md`).
2. **`data/data/`** (~480 МБ, приехал с Windows) — старая копия каталога данных
   с прежним `wt-cookies.json`. В `replays/` части 28 боёв: 9 уже в базе, 19
   нет (14 `expired`, 5 `error`; на CDN их уже нет). Решить, разбирать ли их
   вручную, затем удалить каталог.
3. **Сезон с форума.** При смене формата поста `wt-clan-season` упадёт с ошибкой
   разбора (видно на дашборде) — поправить `src/clan-season-forum.ts`; прежнее
   расписание в базе сохранится.
4. **Публичный сайт.** Туннель до внешнего reverse proxy поднят,
   `WEB_TRUST_PROXY` задан; на прокси осталось настроить сайт и TLS (адреса не
   коммитить: репозиторий публичный). Восстановление после перезагрузки
   сервера и смены его IP не проверялось. `POST /api/player-stats` (кнопка
   «обновить», форма дашборда) ставит запрос к профилю warthunder.com через
   браузер (и к StatShark, если включён) — для анонимных посетителей отключить
   (`WT_PLAYER_STATS_ENABLED=false`) или держать сайт за токеном. Discord
   OAuth — отдельное решение.
5. **Свежесть образа.** Chromium и пакеты Debian обновляет только пересборка
   без кэша (README, «Боевой запуск в Docker»): решить — вручную или таймером
   systemd и в какое время (перезапуск ненадолго останавливает анонсы).

## Код

- `buildClanSnapshot` — синхронно на main thread, 89–103 мс на перестройку раз
  в минуту, пока сайт открыт (последние снимки ПКР 29 мс, ростер 24 мс,
  остальное JS). В worker на main thread осталось бы ~13 мс приёма снимка
  (3 МиБ) — сделать до публичного сайта; нужны параметры `database` у четырёх
  функций чтения и запасной путь для `:memory:` в тестах.
- Checkpoint WAL на main thread: у main-подключения `wal_autocheckpoint` по
  умолчанию, и коммит, переваливший 1 000 кадров, синхронно переносит весь WAL
  (3 000 кадров — 23 мс). Пока ingest делает checkpoint сам, паузы редкие,
  ~10 мс; при росте записи — `wal_autocheckpoint = 0` на main и периодический
  checkpoint в worker.
- ECS 2.59: нет сериализатора нового типа `0xcfad499d` (подвесное вооружение
  `rocket`/`payload`), часть `ri_gpu_object` не разбирается. Убийства и
  траектории не страдают (сущности изолированы), но эти сущности теряются.
- Миграции: сезонные таблицы и часть индексов создаёт bootstrap DDL вне
  реестра `PRAGMA user_version`.
- Ретенция `clan_rating_snapshots`, `clan_rating_history`,
  `player_external_snapshots`: решить срок хранения.
- Внешние ключи (`ON DELETE CASCADE` у таблиц игроков и этапов сезона)
  объявлены, но `PRAGMA foreign_keys` выключен — каскады не работают; дочерние
  строки код удаляет сам, нарушений нет (`foreign_key_check` 2026-10-02).
  Включить после проверки целостности или убрать объявления.
  `INSERT OR REPLACE` есть только у `battle_events` без внешних ключей —
  каскадного удаления при замене не будет.
- Запросы по игроку на холодном кэше ~120 мс (случайные чтения
  `battle_players`; тёплые — 1–5 мс, а после перевода блобов база целиком
  помещается в кэш ОС). Станет заметно — покрывающий индекс
  `battle_players (user_id, session_id, …)`, ~+35 МиБ.
- Web: `@fastify/compress` для крупных JSON (`/api/vehicles` — 226 КБ, gzip —
  43 КБ), ETag для неизменяемых ответов.
- Дашборд `/`: ~1 000 строк inline-скрипта без типизации в
  `src/web/routes/pages.ts` — вынести в `.ts`, собираемый `tsc`.
- SPA, доступность: маркеры таймлайна и строки ленты событий в
  `ScenePlayer.tsx` — `<span>`/`<div>` с `onClick` без клавиатуры; заменить на
  `<button type="button">`. Стрелки в `SegControl`.
- Крупные функции: `buildHeatmapSvg` (~710 строк), `extractReplayEventsProfiled`
  (~240), `src/db/index.ts` (~6 700 строк) — разбивать после стабилизации.

## Сбор и показ статистики (начато 2026-09-29)

- **Сверка источников.** Сравнить данные всех парсеров (реплеи, профиль сайта,
  companion, StatShark, лидерборды), найти и разобрать расхождения. Свести в
  единую статистику, а где нельзя или неудобно пользователю — показывать
  раздельно; совпадающие показатели сверять между источниками, чтобы ловить
  ошибки. Уже известно: StatShark хранит режим как `simulator`, остальной код —
  `simulation`; фраги профиля сайта и StatShark считаются по-разному
  (расхождение до 12×), сравнимы только бои, победы и поражения.
- **БР техники из датамайна.** `economicRankArcade/Historical/Simulation` из
  `wpcost.blkx` → `VehicleInfo.br` (БР = ранг / 3 + 1). `wt-vehicles.json`
  собирается один раз навсегда — нужны версия формата и срок годности: БР
  меняется с патчами, обновлять автоматически после патча (или по статьям об
  изменениях БР). Затем БР на сайте и проверка недельных лимитов этапов сезона
  по технике в боях (в worker сводки).
- **StatShark: что не показано.** Страница игрока показывает уровень, звание,
  даты, историю кланов и ников, места в рейтингах WT (`account_json`), но не
  `ratingsNeo` (своя шкала StatShark, смысл не документирован) и
  `vehicleHistory` (поля — числовые коды). Разобрать все страницы StatShark и
  назначение каждого поля, при необходимости — по сохранённому HTML.
- **`_id` клана как ключ.** Номер с лидерборда не меняется вместе с тегом:
  связать по нему кланы, сменившие ядро тега, вместо `clan_core` (ростер,
  история рейтинга, бои под старым тегом). Собирается с 2026-10-01;
  2026-10-02 — первый случай: клан сменил тег вместе с ядром, номер тот же.
  Открытый вопрос — показывать в старых боях нынешний тег клана или тот, что
  был в момент боя.
- **Ещё не собирается** (решить, нужно ли): поиск игроков `searchplayers` (до
  100 ников по началу, только ник; нужен браузер) — подсказка ника для
  `/api/player-stats`; рейтинг игроков `community/leaderboard` (топ-2020 по
  режиму и сортировке, числа округлены до «105.0K»); WTCS
  `text/wtcsleaderboard` (киберспорт); `clan_activity_by_periods` (смысл
  неясен).

## Продукт

Данные для всего ниже уже собраны; агрегаты считать при ingest или фоном, не
по HTTP-запросу.

- **Метастатистика техники**: win rate и K/D по машине, матрица «кто кого
  убивает» (`battle_kills.killer_model × victim_model`), эффективность оружия
  (`weapon`), техника по карте; классы — из `data/wt-vehicles.json`.
- **Ветка боя** (`air`/`ground`/`mixed`) из `battle_players.vehicles` и словаря
  техники: поле `battles.branch` и серверный фильтр. На 2026-09-28 все бои —
  наземные с авиацией: ценность низкая, пока нет других режимов.
- **Клан против клана**: история встреч, серии, средний счёт по противнику
  (`battle_players.clan_tag`, `team`, `battles.team_won`).
- **Карты**: словарь `levels/*.bin` → человеческое название, затем win rate
  стороны, длительность и места смертей (`battle_kills.victim_x/y/z`).
- **Внешняя статистика игроков**: развивать или заморозить (снимки есть у 6
  identity; витрины не строить до реальных данных).
- **Нельзя**: аналитика отрядов — `battle_players.squad_id` на деле маркер
  команды (4096/4097). Postgres, Rust и GPU — не цели сами по себе.

Наблюдения о качестве данных реплеев —
[docs/replay-data-quality.md](docs/replay-data-quality.md).
